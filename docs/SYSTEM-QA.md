# System.qa and the QOS app model

This is the userspace-architecture layer: `.qa` app archives, a static
permission flow, and `System.qa` as the launcher/FSProcess that starts
the platform. It builds on the pieces that already existed -- the
VFS-as-actors namespace (vfsh2.fpr), the append-only disk log
(diskfs.fpr), and the cell-buffer TUI (stui.fpr).

    make run-system                 # boot System.qa in QEMU (rv64)
    make run-system TARGET=rv32

## The bootstrap flow (what actually happens on boot)

    crt0.S  ->  fpr_rt_init         # buddy over the heap; harts; actors
            ->  fpr_fn_main         # main IS System.qa (actor 0)
                  |
                  |  reads its own config (inline mini-TOML); the key
                  |  `startup = "TUIAppLauncher"` names the first app
                  v
                launch io "TUIAppLauncher"       # through the perm gate
                  |
                  v
                launcher_main caps               # the grid; "just an app"
                  |  reads /services/apps, draws via /services/display,
                  |  takes keys via /services/keyboard
                  v
                pick "TUINotes" -> launch -> tuinotes_main caps  # nested

`main` sets up the device registers ONCE (uart LSR/data, CLINT mtime)
and threads them as a capability triple `(con, me, clk)`. Nothing below
`launch` ever touches a device -- apps speak only URL-addressed services.

## `.qa` archives (docs/QA-FORMAT.md has the byte layout)

A `.qa` is `QAR1` magic + a section table + payloads. Two sections:
MANIFEST (a minimal TOML subset) and ELF (the bundled binary). The
manifest carries the app id, its entry symbol, and -- crucially -- the
permission set, which cannot be separated from the code.

Apps live ON THE DISK: `tools/mkdisk.py` seeds `disk.img` with each
built `.qa` as its own QLOG record (`apps/<Id>.qa`) plus an
`apps/index` record.  System.qa discovers the installed set from the
index and reads each `.qa` off the log ON DEMAND at launch, through
the same storage actor the kv streams use.  The rodata registry
(`runtime/apps_data.c`, generated by `tools/genapps.py`) remains only
as the DISKLESS FALLBACK, reachable through `Apps.*` (`runtime/apps.c`):

    Apps.list  Unit    -> String    newline-joined app ids (fallback)
    Apps.read  id      -> String    the raw .qa bytes (fallback)

Name-dispatch is DEAD: Apps.entry/Apps.run and the genapps entry table
are deleted.  The launcher is System.qa's builtin shell (it cannot be
a process while there is one slot -- the shell could never nest-launch
anything); TUIClock, TUINotes, and HelloProc are real loaded
processes.  The storage actor reads through a boot-scan INDEX now
(one log pass at start; appends extend it incrementally).

## The static permission flow

`System.qa` reads `/apps/<id>.qa`, parses the manifest, and for every
required + optional permission asks the user to grant it. Then:

- ALL required granted  -> the app runs, receiving ONLY the granted
  capabilities as an opaque `caps` value. Its services (`svcReadKey`,
  `svcWrite`, `svcClock`) check the granted set at each call, so a bug
  that touches an ungranted service faults loudly instead of silently
  working.
- ANY required denied    -> the app does not run; the launcher prints
  exactly `Cannot Run Application without all required compulsory
  Permissions`. Denying a required perm persists nothing, so the next
  launch asks fresh.
- Optional denied        -> launch proceeds; the app simply is not
  handed that capability and adapts (TUINotes: "[offline: net not
  granted]").

Grant decisions PERSIST: when a launch proceeds, the full decision set
(required + optional, grants AND denials) is appended to the log at
`sys/perms/<aid>` -- readLatest wins, and the record is only
re-appended when a prompt was actually shown, so plain reruns don't
grow the log.  On later launches (same boot or after a QEMU restart)
each remembered decision replays silently, echoed as
`grant <url> (<mode>) ? [remembered y]` in the prompt's place.  A
required perm remembered as DENIED is re-asked rather than replayed
(a manifest can promote an optional to required; auto-denying forever
would brick the app).  `make wipe-disk` forgets everything; a QDEL
(storage tag 4) on `sys/perms/<aid>` forgets one app.

Everything -- including TUIAppLauncher itself -- goes through this same
gate. The launcher is not privileged; it asks for keyboard/display/
clock/apps like any app.

## /services/modules: the URL method for module identity

Runtime module resolution is a URL-addressed, permission-gated service
like any other. An app that was granted `/services/modules` (read) may
call `svcModFn caps "<hash>/<fn>"`; the answer is `(1, fn)` or `(0, 0)`
— a miss is data, because a resolver that panics on absence cannot
front a disk module store or a remote FPRLive peer, where misses are
routine. The backend today is the link-time module table
(`Mod.resolve`, runtime/mod.c); swapping in `.qa` module archives from
disk or remote resolution changes `svcModFn` only — no app, no URL, no
permission change. TUIClock's optional `/services/modules` permission
is the shipped demonstration (grant → pad2 resolved by hash at runtime;
deny → builtin formatting, stated on the line).

## Storage (docs/STORAGE.md has the full architecture)

The default setup has a disk: one append-only QLOG page log carries
installed `.qa`s (`apps/<Id>.qa`, overriding rodata), each app's
persistent kv msg stream (`apps/<Id>/<Id>.kv`, Sol's Persistent model
as event sourcing -- append msgs, replay folds), and System.qa's own
boot beat (`sys/boots`). The log is owned by a storage actor
(mods/qlog.fpr, a separately compiled `use` module) and reached only
through the `/services/storage` capability; an app's kv url is built
from its capability, so cross-app addressing is structurally
impossible. Diskless boots degrade: storage answers `Err "no disk"`.

## The TUI module: how apps look and move

Apps render through `mods/tui.fpr` -- stui's proven engine (packed
cell buffers, vbox/hbox layout with fix/flex sizing, borders, the ANSI
diff renderer with dirty-run merging) as a separately compiled `use`
module with one architectural change: every emitting function takes a
writer `String -> Unit`, and apps pass `svcWrite caps` -- rendering
flows through the display capability, and the module compiles against
nothing but the prelude. `svcPollKey` (same keyboard capability,
nonblocking) is what makes apps DYNAMIC: the launcher ticks a live
clock in its header between keystrokes, the clock app repaints only
the changed digit cells each second and rotates its colour each
minute, and the notes editor live-persists each committed line while
repainting only the rows a keystroke touched. `tests/tuitest.fpr`
pins the cross-unit rendering contract.

## Apps are ordinary FPRISC

An app is a function `name caps = ...` that uses only the `svc*`
helpers. It never sees a device register, an actor primitive, or a
launcher internal. TUIAppLauncher is the proof: a paginated grid of app
icons with a header bar (clock + count + page), built entirely on
`/services/{apps,display,keyboard,clock}`. Selecting an app re-enters
`launch`, so the launcher is an app that launches apps.

## The ELF seam (name-dispatch today, real loader later)

The image is ONE statically-linked binary right now, so `launch`
resolves the manifest `entry` symbol against apps CO-COMPILED into
System.qa and dispatched by name (`Apps.entry` -> `Apps.run`), exactly
like the existing `Mod.fn hash name` module path. The `.qa`'s ELF
section is still bundled and hashed; it is simply not yet mapped.

When the real ELF-in-ELF loader lands (relocation + a per-FSProcess
address space + an entry trampoline -- a separate build), only ONE
function changes: `runEntry` grows a `LaunchElf` branch that maps the
`.qa`'s ELF section into a fresh process and jumps to its entry with the
same `caps`. No app changes, no manifest changes, no change to the
permission flow. The architecture is designed around that seam.
